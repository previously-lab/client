## 0. 一句话定位

Previously Client 是跑在用户本机（macOS / Windows）的 **Previously 内核本地实例 + 本地感知末梢**，以 npm CLI 形态分发。它不是 Previously 的复刻，而是同一内核的第二个入口。

## 1. 设计理念

### 1.1 壳，而不是内核

Client 内部启动的是 **agent 仓库的本地构建产物**（Next.js standalone server + Local World + `STORAGE=local` + `PREVIOUSLY_MODE=client`）。本仓库不包含 agent 逻辑的任何副本：没有人格、没有 slicer、没有上下文组装——那些全部来自被打包进来的 agent 仓库产物。Client 仓库自己只拥有三样东西（第四样 Connect 暂缓封存，见 §8）：

1. **进程壳**：安装、启动、停止、升级、自恢复
2. **感知末梢**：监听本机其他 Agent 的对话并抄录为时间片
3. **能力出口**：MCP server，把本地记忆暴露给本机其他 Agent
4. ~~**Connect 客户端**~~：与云端 Previously 的消息通道（**暂缓封存**）

这样"两个项目一起工作"在物理上成立：agent 仓库的任何内核更新，client 发版时自动继承。**不抽取 `previously/core` 公共仓库**——共享通过打包产物实现，client 版本与内核版本绑定升级，接受 breaking change（与 Previously 自身演进策略一致）。

### 1.2 用户成本是第一设计约束

目标用户是 **AI 用户，不一定是程序员**。成本敏感排序：

- **首选：订阅桥接**。用户本地已有 Claude（Pro/Max）、Codex、Kimi Code 等订阅 → client 直接驱动这些 CLI 的 headless 模式作为执行后端，用户边际成本为零。这是一期就做的能力，不是高级选项。
- **次选：自备 API key**。无订阅的用户直接填 key，走 agent 仓库现有的 models.dev catalog 路由。
- **订阅桥接只做"手"，不做"脑"**：外部 CLI 适合接收任务描述 + 组装好的上下文去执行；Previously 的人格、记忆主权、时间片协议仍由内核保证——不依赖向外部 agent 注入 system prompt（Claude Code 支持 `--append-system-prompt`，Codex 靠 AGENTS.md，注入深度不可靠，不押注）。

### 1.3 为什么不是 Tauri/Electron

- 受众装着 Node 生态工具链，`npm i -g` / `npx` 零门槛
- 绕开签名/公证/发布者证书的全部成本
- Web UI 直接复用 agent 仓库的 Next.js 界面（localhost 打开即"GUI"）
- 先例：Claude Code、Kimi Code、Gemini CLI、DSH 全是此形态
- Node 性能不是瓶颈：workload 是 LLM API 往返（秒级）+ 文件 I/O（毫秒级）；常驻内存 200–400MB 与同类产品同量级

### 1.4 数据三级存储

安装时让用户三选一（`previously init` 引导）：

1. **本地临时目录**（`~/.previously/memory/`）：零门槛上手，纯本地
2. **用户自己的 GitHub 数据仓**：配置 token 后本地直接读写/提交，与云端天然同步
3. **连接云端托管**：作为云端实例的本地镜像（**依赖 Connect，随之一并暂缓**；一期实际提供前两项）

数据仓无版本号：目录结构即现状即契约，索引类文件永远可从切片原文确定性重建（详见姊妹文档 §3.3）。

"放弃 GitHub、云端记忆直接远程放本地"的反向模式**明确不做**：可用性强绑本机在线，NAT/休眠全是坑，且摧毁云端的连续性卖点。

## 2. 命令面

```
previously init       # 引导：选存储形态、选执行后端（订阅桥接 / API key）、生成配置
previously start      # 后台拉起内核（standalone server, local world），打开浏览器
previously stop       # 停止
previously status     # 内核状态、抄录器状态、执行后端健康
previously install    # --claude / --codex / --kimi：写入各家 MCP 配置与 hooks
previously watch      # 前台跑抄录器（start 默认已含，此命令用于调试）
previously logs       # 内核与抄录器日志
previously upgrade    # 升级内核产物版本
# 受限记忆工具（bridge 阶段级外包用，见 §7.3，实验性）：
previously recall     # "<query>"：子串搜索，只返回指针（slice id + 行号 + 摘录）
previously readslice  # <sliceId> [--start N --end N]：读取一个切片的完整对话记录
previously timeline   # [--month YYYY-MM] [--day MM-DD]：人类时间线，可按月/日收窄
previously strands    # [name]：列出全部 strand，或某个 strand 的切片 id
previously card       # [--slice <sliceId>]：活卡或切片卡片快照
previously slicesummary # <sliceId>：只输出切片 frontmatter
previously agentlog   # <sliceId> [--start N --end N]：切片认知记录

# 以下随 Connect 暂缓封存，不在一期命令面：
# previously connect    # <配对码>：与云端 Previously 配对
# previously disconnect # 吊销本地凭据
```

原则：命令少而正交；所有守护逻辑（pid 文件、daemonize、崩溃重启）收敛在 `start`/`stop` 一处；不做开机自启（一期）。

## 3. 架构分层

```
┌─ CLI (bin) ─ 进程管理、配置
├─ Kernel ──── agent 仓库 standalone 产物（localhost:PORT, PREVIOUSLY_MODE=client）
│               └─ Local World（.workflow-data 落盘 ~/.previously/）
├─ Scribe ──── 抄录器：fs watch 各 Agent 会话日志 → 切片管线 → 写入本地 memory
├─ MCP ─────── stdio MCP server：read_timeline / read_slice / list_strands / search_memory（只读）
├─ Bridge ──── 订阅桥接：Claude Code / Codex / Kimi Code headless 驱动
└─ Connect ─── 【暂缓封存，见 §8】
```

层间约束：Scribe 和 MCP 只读写 memory 数据，不进入内核进程；Bridge 由内核的工具层触发。

## 4. 时间片并发语义（与姊妹文档 §4 对齐）

- 时间片身份严格绑定**开始时刻**；任何来源（内核、抄录器）的对话都是独立时间片，不存在"接续别人的时间片"。
- **多写者并发写同一条时间线是设计内行为**：不要求串行，允许时间重叠。
- 文件级冲突不存在（slice id 独立命名）；索引类文件由 `weaveTimeline` 确定性重建，写入顺序无关。
- 抄录器的幂等以文件偏移量 + 内容 hash 为增量游标；重复抄录产生的是重复切片而非数据损坏，重建时按内容 hash 去重。

## 5. 感知末梢：抄录器（Scribe）

### 5.1 理念

**抄录，不劫持**。Client 对其他 Agent 的对话流是只读观察者：读取本地会话日志，按 Previously 的时间片协议重组，写入本地 memory。永远优先于通过 hooks 向别人上下文注入内容（hook 注入作为后续可选项，且只写"已归档"类标记）。

这等于把其他 Agent 变相变成"符合 Previously 标准的时间上下文生产者"——用户的全部 AI 对话历史，无论由哪个 Agent 产生，最终汇聚成同一条时间线。

### 5.2 数据源（一期四家全部落地：C3 落地 Claude Code/Codex，C6 落地 Kimi Code/Gemini CLI）

| Agent | 会话日志位置 | 格式状态 |
|---|---|---|
| Claude Code | `~/.claude/projects/<path-slug>/<session-id>.jsonl` | 有第三方文档，append-only 事件流 |
| Codex | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` | 无官方 schema |
| Kimi Code | `~/.kimi-code/sessions/<workDirKey>/<sessionId>/agents/<agent>/wire.jsonl` | 无官方 schema；C6 已对本机 82 个真实 wire.jsonl（protocol 1.5）实测；`kimi export` 是稳定备选通道 |
| Gemini CLI | `~/.gemini/tmp/<project_hash>/chats/` | 无官方 schema；C6 按整文件 JSON checkpoint 假设实现（本机无安装，ASSUMED），retention 清理可能中途删文件 |

### 5.3 必须接受的代价

- **格式税**：各家 schema 无官方规格，升级可能漂移。对策：解析器按家隔离成插件；解析失败降级为"原文附录"切片而非报错中断（同时按 §9 失败哲学如实上报）。
- 切片产物与内核自产切片**同构同目录**，在 strands/timeline 中平等可见，但带来源标签（`source: claude-code` 等）。

## 6. 能力出口：MCP Server

本地 stdio MCP server，向本机所有 Agent 暴露**只读**记忆工具：`read_timeline` / `read_slice` / `list_strands` / `search_memory`。实现上直接复用 agent 仓库产物中的 episodic 读取函数，不经过 HTTP。

`previously install --claude` 等命令负责写入各家配置文件（Claude: `.mcp.json`；Codex: `config.toml`；Kimi: `mcp.json`），卸载对称。

这是整个 Client 中**差异化最大、别家最难抄**的部分：其他 Agent 由此获得"用户全部过去"的读取能力。

## 7. 订阅桥接（Bridge）

### 7.1 驱动方式（均已验证可行）

- **Claude Code**：`claude -p` + `--output-format stream-json` + `--append-system-prompt` + `--max-turns/--max-budget-usd`；订阅 OAuth 直接可用（注意 `--bare` 不读 OAuth）
- **Codex**：`codex exec --json`，官方 TS SDK `@openai/codex-sdk`；指令注入走 AGENTS.md
- **Kimi Code**：`kimi -p` + `--output-format stream-json`；另有 `kimi web`（本地 REST/WS + OpenAPI）可能是更顺的集成入口

### 7.2 边界

- 桥接器负责：任务描述 + 上下文组装（来自本地时间片）→ 驱动 CLI → 回收结果 → 结果落时间片
- 桥接器不负责：人格一致性、长程记忆协议——那些是内核的事
- 每家一个适配器，接口对齐（`dispatch(task) → stream events → result`），冷启动成本与配额策略在适配器层消化

### 7.3 阶段级外包（phase outsourcing，**实验性**）

> 注：`docs/design/client-mode-direction.md` §3 曾定论「Bridge 模式：只保留，不扩展」。本节是**验证阶段对该决策的部分反转**：为验证「整阶段一次 bridge 调用」能否显著降低延迟，bridge 契约新增一个可选 `phase` 字段。验证有效后再系统化为正式能力；验证失败则整节回滚，旧路径（无 `phase`）始终保持字节兼容。

委托粒度从「每个 agent 一次调用」改为「每个 workflow 阶段一次调用」：

- **payload 扩展**：`bridge-exec` stdin 增加可选字段 `"phase": "chat" | "housekeeping"`；非法值按用法错误 exit 2。无 `phase` = 现有通用 memory 文档，内核 `delegateTask` 旧路径不变。
- **受限记忆工具**：client agent 只能通过以下七个本地 CLI 子命令访问记忆，禁止用文件工具直读记忆目录、禁止在记忆根下做任何写操作（持久化是内核的事）：
  - `previously recall "<query>"` —— 子串搜索，**只返回指针**（slice id + 文件角色 + 行号 + 短摘录），另附时间线尾部条目；输出上限 ~30k 字符，截断时明示。契约同内核：recall 给指针，引用细节前先用 readslice 打开切片。
  - `previously readslice <sliceId> [--start N --end N]` —— 输出切片的完整对话记录（`timeline/core.md`），支持 1 起始闭区间行范围；同样的 ~30k 上限与截断说明。
  - `previously timeline [--month YYYY-MM] [--day MM-DD]` —— 人类时间线，可按月/日收窄。
  - `previously strands [name]` —— 列出全部 strand（含切片数），或输出某个 strand 的切片 id（每行一个）。
  - `previously card [--slice <sliceId>]` —— 活卡（`current-previously.md`）或某切片的卡片快照（`previously.md`）。
  - `previously slicesummary <sliceId>` —— 只输出切片 frontmatter（focus/summary/tags/tone 等），不含正文。
  - `previously agentlog <sliceId> [--start N --end N]` —— 切片的认知记录（`timeline/agent.md`），行范围同 readslice。
  - 全部命令复用 `src/lib/memory.ts` 的只读实现（严格 slice id 校验 + 路径穿越防御）；无匹配/空结果 exit 0，记忆未初始化等运行时错误 exit 1，用法错误 exit 2。
- **三层能力原则**：① 客户 agent 的原生能力（联网搜索、深度推理）——不重复实现，也不在 skill 文档中提及，完全放手；② Previously 独有记忆能力（读切片/时间线/卡片/strand）——实现为上述 CLI 命令，经 skill 文档注入；③ Previously 工作协议（如 recall 方法论：指针非内容、一次 recall 即停、可用子 agent 隔离搜索噪声）——经 skill 文档作为操作手册注入。
- **阶段 skill 文档**：`phase` 存在时，每次调用的临时 workspace（CLAUDE.md / AGENTS.md）携带阶段专属文档而非通用 memory 文档：
  - `chat`：角色（带分层 episodic memory 的个人 agent）+ 上述七命令工具契约 + Previously recall 协议（recall 给指针非内容、引用细节前先 readslice 打开切片、一次 recall 即停；prompt 里的 card 是索引不是档案；runtime 支持子 agent 时把 recall 搜索交给只带记忆命令的子 agent 以隔离搜索噪声）+ 输出契约（终稿原样渲染进 web chat UI）。原生能力（深度推理/联网搜索）按三层原则一字不提。
  - `housekeeping`：整个阶段的职责——线索提取（tags merge-first：reuse ≤5 / create ≤3；semantic_hint；intent 六选一；memory_worthy 为 false 时 tags 必须为空；memory_update 仅在用户显式要求记录/自进化时给 focus 串；emotional_signal）+ closed_marking（仅当任务输入说明切片关闭时必填）+ 自进化门控（拿不准一律 worth=true——浪费一次 review 便宜，漏掉一次进化是永久的记忆丢失）+ 卡片 mutation 词汇表（setIdentity / updatePastProfile / addPastAnchor / removePastAnchor / addNow / removeNow / promoteNowToPast / addHorizon / resolveHorizon / addSelfModel / removeSelfModel）+ 取证纪律（self-model 教训必须先用 recall/readslice 取证）+ **backfill_marks**（仅当 context 带 "Dry slices needing marks" 区段时，为每个列出的干片产出一个 `{slice_id, focus, summary}` 标记，slice_id 逐字照抄、最多 3 条，无此区段返回 []——旧版每片一次独立子 agent spawn 的干片补标记由此并入同一次调用）+ **strand_merges**（仅当 context 带 "Strand merge candidates" 区段时，为近似重复 strand 提 from→to 合并——`to` 必须从候选列表逐字照抄、不成链、拿不准不合并、最多 30 条，无此区段返回 []——旧版 strand-consolidator 子 agent 的 LLM 合并由此并入同一次调用）。
  - **housekeeping 输出契约**：最终回复必须是且仅是一个符合固定 schema 的 JSON 报告 `{ analysis, closed_marking, evolution, backfill_marks, strand_merges }`——无 markdown 围栏、无任何前后散文；内核负责工程验证（strand 名校验、mutation 上限、backfill 只认提供过的候选 id、strand 合并只认提供过的候选键且双键须存在于 prune 后索引、确定性兜底）并落盘。
- skill 文档保持完全静态（只有 `{{MEMORY_ROOT}}` 一个占位符）；每轮动态数据（本轮消息、card、strands menu、报告 schema 细节）由内核组装进 payload 的 task/context。

## 8. Connect 客户端（**暂缓 · 设计存档**）

> 本章整体暂缓实施，随姊妹文档 §5 一并封存。启用条件：云端基建出现可接受成本的长连/推送能力。以下为封存前的设计结论。

### 8.1 传输（设计存档）

**语义上服务端主动，物理上客户端主动。** 本端不监听任何端口：

- **长轮询信箱**：挂起的 GET 请求云端信箱端点取走自己的任务消息；超时即重发。对语义层等价于云端实时下发。
- **接口维度回调**：`task.result` 与 `heartbeat` 为普通 POST。
- 无持续连接、无会话状态、每条消息自包含。
- 备选（真云端直连的唯一物理出路）：客户端内置隧道进程（Cloudflare Tunnel 类）。封存期间不实施。

### 8.2 鉴权（设计存档）

本期从简方案（ACCESS_SECRET 级凭据）随封存一并失效。启用时直接进入系统性方案：设备密钥对、GitHub 数据仓即信任根、信封加密，设计方向见姊妹文档 §7.2。配对码流程同属该批次。

## 9. 失败哲学

**任何错误都必须及时、如实地告知用户或调用方（含 Agent 自身），使其能做出响应和判断。**

- 抄录器解析失败 → 降级为原文附录切片 + 显式状态上报，不静默丢弃。
- Bridge 驱动失败（CLI 不在、配额耗尽、超时）→ 以结构化错误返回内核，由内核决定重试/换后端/告知用户。
- 内核崩溃重启 → 按"运行时状态丢失即新时间片"语义重新开始，并在新时间片中如实记录中断事实（local world 内存队列丢 step 同属此类）。
- 任何后台循环的无限重试都必须有退避与上限，并最终以错误形态浮出水面。
- （Connect 封存期）Connect 相关的失败语义随 §8 一并存档。

## 10. 打包、分发与内核供应链

### 10.1 内核供应链（设计决定 v4，v5 细化）

**client 的内核产物永远从指定的 agent 仓库（线上版本仓库）的指定 ref 构建。** 供应链脚本接收仓库地址 + ref（分支/tag/commit），克隆 → 构建 standalone → 安装到 `kernelDir`。由此获得：

- **测试/线上联动**：构建 ref 指向 `main` 即线上联动，指向 feature 分支即测试环境联动——同一套逻辑，不同参数。
- **联合部署**：无意外时两边一起部署；client 发版 = 锁定一个内核 ref + 发布 npm 包。

**v5 发布形态（设计决定）**：内核以独立 npm 包 `previously-kernel` 发布，作为 client 包的 npm 依赖被自动带入——用户永远只装一个包、跑一条命令。agent 仓库每次打版本 tag → CI 自动构建 + 发布内核包，发布纪律由流水线保证，无人工环节。用户机器上永远不发生编译。

**v5 出厂标准（设计决定）**：standalone 产物发布前必须经 `scripts/pack-standalone.mjs` 完全 dereference（符号链接→实体文件，含 pnpm 依赖上下文内嵌），产物为零链接纯文件树。这是 Windows 支持的必要条件，而非平台补丁：三个平台共用同一份产物，安装、复制、运行全链路无链接处理。已在 v0.8.0 产物上真机验证（34 个链接 dereference 后，client 安装 + 启动 + UI + /api/version 全通，无需任何手工修复）。

### 10.2 版本策略（设计决定 v4）

client 与内核**解耦更新、按 minor 版本线绑定**：

- client 内嵌一条内核版本线：client 0.8.x ↔ 内核 0.8.x。patch 级（0.8.1 → 0.8.2）在内核侧自由演进。
- `previously upgrade`：查询 agent 仓库的版本 tag，在当前 minor 线内装最新 patch；跨 minor（0.8 → 0.9）拒绝并提示"请先升级 client"。即内核 0.9 不允许 client 0.8 继续使用更新。
- 内核 standalone 产物必须携带可机读的版本标识（版本文件或 HTTP 端点），client 在 `start`/`status`/`upgrade` 时读取并做兼容校验。
- 内核更新原子化：新版本安装到独立目录，切换软链/指针，失败可回滚到上一个版本。

### 10.3 其余分发决策

- npm 包 `previously`（scoped 名待定），`bin` 入口
- 发布物内嵌按 §10.1 构建的 standalone 产物；`start` = fork `node server.js` + 环境变量注入
- fs 监听用 chokidar（跨平台坑已处理），不裸用 `fs.watch`
- 远期兜底：`bun build --compile` / Node SEA 单二进制；不影响 npm 首发

## 12. 剩余真实风险（非设计留白，属执行验证）

- standalone 产物随 npm 包发布的体积与安装时长（可能逼出"安装时下载内核产物"的备选发布形态）
